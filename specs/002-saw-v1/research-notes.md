# connectivity

## Summary
Researched four routes to "invite by email, zero network config" connectivity for SAW's existing Node/TypeScript WebSocket+SQLite relay. The standout 2026 development is Iroh 1.0 (shipped June 15, 2026 by n0): dial-by-public-key QUIC with built-in NAT hole-punching (~90% direct connections), automatic fallback to free public relays, MIT/Apache-2.0 dual license, and official Node.js bindings (@number0/iroh) with wire-protocol stability guarantees — it lets SAW keep its relay exactly as-is and just swap the "how do peers reach it" layer, dropping the Tailscale requirement. The alternatives all have a disqualifying flaw for v1: js-libp2p's hole punching is admitted by its own maintainers to be unreliable in Node (needs QUIC, which Node lacks), raw WebRTC data channels require running a signaling server plus a TURN server for the ~10-15% hard-NAT cases, tsnet is Go-only (forcing a sidecar binary) and Tailscale/Headscale reintroduces either account friction or a self-hosted control plane, and Matrix means operating an AGPL homeserver with a domain and TLS just to move small JSON messages. A Cloudflare Tunnel remains the best zero-cost escape hatch if a member wants a plain HTTPS/WSS URL for the relay.

## Findings
- Iroh 1.0 (n0-computer/iroh, https://github.com/n0-computer/iroh) shipped June 15, 2026 with wire-protocol and API stability guarantees: a v1 endpoint talks to any other v1 endpoint regardless of patch version or language binding. Dual-licensed MIT/Apache-2.0. ~10k GitHub stars; n0's public relay infrastructure was already carrying 200M+ endpoint connections/month at launch.
- Iroh's model fits SAW exactly: every node gets a 32-byte cryptographic NodeId (an ed25519 key) and you dial the key, not an IP. NAT traversal via simultaneous-outbound holepunching succeeds in roughly 9 of 10 real-world network configurations (per https://docs.iroh.computer/concepts/nat-traversal); when it fails, traffic transparently keeps flowing through the relay. Net effect: effectively 100% connectivity anywhere outbound traffic works, with ~90% of pairs going direct (local-first, no third party sees traffic).
- Iroh's unavoidable server component is the relay (rendezvous + fallback), but n0 hardcodes free public relays suitable for development/testing, and the production relay implementation (iroh-relay, https://github.com/n0-computer/iroh/tree/main/iroh-relay) is the same open-source MIT/Apache binary n0 runs — self-hosting is a single binary on any VPS. Cost for SAW v1: $0 (public relays), later ~$5/mo VPS for a dedicated relay.
- Iroh has official Node.js bindings: npm package @number0/iroh, generated via napi from the iroh-ffi repo (https://github.com/n0-computer/iroh-ffi), documented with JavaScript examples at https://docs.iroh.computer/languages/javascript. Node.js is one of the four officially committed 1.0 SDK bindings (Python, Node.js, Swift, Kotlin). Caveat: Node-only, explicitly NOT for browsers (iroh-ffi issue #223) — a future SAW web UI must reach the relay over plain HTTPS/WSS or via the local CLI daemon, not over iroh.
- User-visible setup with iroh: member A runs `saw up` (relay + iroh endpoint start, keypair generated automatically), sends an invite string/ticket (NodeId + room token) by email; member B pastes it into `saw join`. No port forwarding, no Tailscale, no accounts, no DNS. This is the closest match found to the founder's 'invite by email, a couple commands' bar.
- js-libp2p is NOT viable as SAW's NAT-traversal layer: libp2p maintainers state in https://github.com/libp2p/js-libp2p/discussions/2388 that js-libp2p 'hasn't put a lot of effort into hole punching' because it needs QUIC to be reliable and QUIC support is still missing in Node.js. Its Circuit Relay v2 fallback is deliberately byte- and time-limited, so relayed connections are not a durable fallback without running your own unrestricted relay. (MIT/Apache licensed, mature project overall — just wrong runtime for hole punching.)
- WebRTC data channels in Node are workable but the highest-ops option: node-datachannel v0.32.3 (libdatachannel bindings, ~107 dependent packages, Node >=18.20, Linux/Win/macOS; https://github.com/murat-dogan/node-datachannel) or werift v0.23.0 (pure-TypeScript; https://github.com/shinyoshiaki/werift-webrtc) are both actively maintained. But you must run: (1) a public signaling server (a WebSocket server — the exact reachability problem SAW already has, recursively), (2) STUN (free public servers exist), and (3) a TURN relay (self-hosted coturn or paid) for the ~10-15% of pairs behind symmetric/hard NATs. Iroh gives the same direct-with-relay-fallback outcome with one integrated library and free public fallback infra.
- tsnet (https://pkg.go.dev/tailscale.com/tsnet) embeds a full userspace Tailscale node in-process with no daemon and no root — but it is Go-only, so a Node/TS codebase must ship and supervise a Go sidecar binary per platform. Tailscale's free Personal plan covers 6 users with unlimited personal devices (https://tailscale.com/docs/account/manage-plans/free-plans-discounts), but joining a tailnet still requires each teammate to create a Tailscale account and complete an SSO login — precisely the friction the founder wants gone. NAT traversal reliability is excellent (DERP fallback, effectively 100%).
- Headscale (https://github.com/juanfont/headscale, BSD-3-Clause, v0.29.1 June 2026, ~38.5k stars, 'mature but not an enterprise product') removes the Tailscale account dependency but requires someone to operate a public control-plane server with a domain and TLS — more standing infrastructure than SAW's own relay, and it still doesn't solve the Go-sidecar problem for a Node codebase.
- Matrix as transport: Synapse and Dendrite were relicensed from Apache-2.0 to AGPLv3 in November 2023 (https://element.io/blog/element-to-adopt-agplv3/) — fine to run unmodified as an ops dependency, but a homeserver needs a public VPS (1-2GB RAM), a fully qualified domain, valid TLS, and specific DNS records; lightweight servers (Conduit family) reduce RAM but not the domain/TLS requirement. Matrix would replace SAW's relay and data model (rooms/events/federation/E2EE for free) rather than make the existing relay reachable — architecturally interesting for the long-term threads vision, disproportionate for v1 two-member connectivity.
- Hosted-tunnel option (a): Cloudflare Tunnel is free with unmetered bandwidth and unlimited tunnels; WebSockets work by default; cloudflared uses QUIC and works from behind any NAT since all connections are outbound (https://dev.to/lightningdev123/top-10-cloudflare-tunnel-alternatives-in-2026-a-practical-guide-for-developers-2akg, https://github.com/anderspitman/awesome-tunneling). Setup: brew install cloudflared, create tunnel, paste token — teammates just get a wss:// URL, zero client install. Costs $0 but stable named tunnels need a Cloudflare account + domain (ephemeral trycloudflare.com URLs need neither); the edge itself is not self-hostable and all traffic transits Cloudflare (only SAW messages/refs, never code, so the boundary holds). ngrok charges $20-40/mo for equivalents and is closed source — dominated by Cloudflare here.
- Reliability comparison (server component / direct-connection share / hard-fail risk): Iroh — tiny relay (free public or self-host one binary) / ~90% direct / near-zero; WebRTC+STUN+TURN — signaling + TURN servers / ~85-90% direct / fails without funded TURN; tsnet+Tailscale — Tailscale's control plane + DERP (or self-hosted Headscale) / high / near-zero but account-gated; Cloudflare Tunnel — Cloudflare edge / 0% direct (always relayed) / near-zero; Matrix — full homeserver / 0% direct / near-zero but heaviest ops.

## Recommendation
Adopt Iroh (@number0/iroh) as SAW v1's connectivity layer: keep the existing WebSocket+SQLite relay logic intact on the host member's machine, but have the relay listen on an iroh endpoint and have `saw join` dial the relay's NodeId from an emailable invite string — this deletes the Tailscale prerequisite with ~90% direct local-first connections, automatic free relay fallback, MIT/Apache-2.0 licensing, and official 1.0-stable Node.js bindings, at $0 operating cost. Keep the plain WebSocket listener as a secondary transport (for LAN/Tailscale users and a future web UI, since the iroh npm package is Node-only and browsers can't use it). De-risk the napi native-module dependency behind a small transport interface; if the bindings prove rough in practice, the fallback is a Cloudflare Tunnel (free, WSS works, zero client install for joiners) rather than libp2p or raw WebRTC, both of which cost more ops for worse Node-side NAT traversal. Revisit Matrix only when the multi-thread/stakeholder-access vision matures — it's a data-model decision, not a v1 connectivity fix.

# landscape

## Summary
The 2025-2026 landscape splits into four clusters, none of which does what SAW's vision describes. (1) Vendor team features (Cursor Teams, GitHub Copilot app, OpenAI Codex app, Claude Code agent teams) are all single-operator multi-agent: one human orchestrating many agents, with team collaboration routed through PRs or chat mentions. (2) Shared-agent chat platforms — most importantly Salesforce's Slack Code, launched August 20, 2026 — put one team-addressable agent into a channel, server-side and chat-first. (3) Transcript-sharing tools (Sourcegraph Amp shared threads, Entire.io, claude-git-sessions) let teammates read raw agent sessions, crossing the boundary SAW deliberately keeps. (4) OSS neighbors (AgentWorkforce/relay, hcom, agentscope-ai/AgentTeams) are the closest infrastructure but remain agent-centric or single-operator. Nobody combines each-developer-keeps-their-own-agent, agent-mediated human-to-human context relay via per-work-item threads, cross-vendor support, local-first transport, and a strict messages-and-git-refs-only privacy boundary — that composite is SAW's open gap, though Slack Code shows the window is narrowing.

## Findings
- Slack Code (Salesforce, launched Aug 20, 2026, free on all Slack plans) is the biggest strategic entrant: tagging a coding agent in a channel opens a 'Code Channel' with an agent space and canvas showing diffs/live previews; supports Claude Code, Devin, v0, ChatGPT and others via API. Explicitly pitched as 'agentic coding is now multiplayer.' But it is Slack-centric, server-side, chat-first, and the agent is a shared participant the team invokes — not each person's own agent relaying their context. https://www.salesforce.com/introducing-slack-code/ and https://siliconangle.com/2026/08/20/salesforce-introduces-slack-code-to-bring-agentic-team-coding-into-the-open/
- Claude Code shipped cross-session messaging in v2.1.224 (ListAgents/SendMessage tools, plain text only, never history or files) — but it is strictly same-account: 'your other sessions,' cross-machine only via Remote Control through Anthropic servers. Anthropic built the single-user version of SAW's plumbing and stopped at the account boundary; its safety design (inbound accept/hold/refuse controls, messages can't approve permissions or change config, loop throttling, size caps, notify_when_idle) is a ready-made spec SAW should copy for cross-member steering. https://code.claude.com/docs/en/cross-session-messaging
- Claude Code Agent Teams (experimental, v2.1.32+, CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1) coordinate multiple sessions of ONE user via a shared task list and mailbox — single-operator, not multi-developer. https://code.claude.com/docs/en/agent-teams
- Sourcegraph Amp is the closest product on 'team-visible AI threads': all threads sync to ampcode.com, are workspace-shared by default, searchable by teammates, linkable in code reviews, with private/group/workspace visibility tiers and a Thread Map visualization. But it shares raw transcripts (crossing SAW's boundary), is server-side on Sourcegraph infrastructure, and is single-vendor (Amp only) — teammates read threads rather than having their own agent answer from them. https://ampcode.com/manual
- Devin (Cognition) embodies the inverse model to SAW: one shared cloud agent the whole team tags in Slack (@Devin), with a team 'Knowledge' base the agent proposes additions to from conversations, and MultiDevin manager/worker hierarchies on Enterprise. Its intake from Linear/Jira/Slack/Teams validates SAW's connector plan; its Knowledge-proposal loop (agent suggests durable team facts, humans approve) is worth stealing. https://cognition.com/blog/devin-generally-available
- GitHub Copilot's collaboration story runs through chat platforms and PRs: @GitHub in Teams/Slack spins up a cloud sandbox and opens PRs; the Copilot desktop app (Build 2026) orchestrates many agents each in an isolated git worktree, including third-party agents (Claude, Codex). Still one human orchestrating agents; no teammate-to-teammate agent context relay. https://github.blog/news-insights/product-news/github-copilot-app-the-agent-native-desktop-experience/
- Cursor Teams offers shared rules, shared team context (org-level config, not per-thread), Bugbot reviews, and a Slack integration where agents work across channels/threads with multi-repo support; Cursor 3 (Apr 2026) runs up to 8 parallel agents on isolated branches. Again single-operator orchestration plus org-config sharing — no agent-mediated inter-person threads. https://releasebot.io/updates/cursor
- OpenAI Codex app manages multiple agents in parallel with cloud tasks for reproducibility, and team plugin sharing via URL with admin-managed private marketplaces (2M+ weekly users by Mar 2026) — enterprise agent platform positioning, but no shared team threads carrying one person's agent context to another person. https://openai.com/index/introducing-the-codex-app/
- AgentWorkforce/relay (Apache-2.0, ~800 stars, active) is the closest OSS infrastructure to SAW's relay: WebSocket messaging with channels, threads, DMs, reactions, files, search, durable delivery, agent status tracking, MCP tools for SDK-less agents, works across machines over the internet, supports Claude/Codex/Gemini. It is agent-first (humans as operators) with no work-item/git-ref semantics and no privacy boundary concept — but it proves the transport layer can be off-the-shelf. https://github.com/AgentWorkforce/relay
- hcom (aannoo/hcom) hooks Claude Code, Codex, Cursor, OpenCode, Kilo and others into a shared messaging/event bus with @mentions, broadcast, transcript watching, agent spawning, a TUI dashboard, cross-device MQTT relay, and — notably — collision detection that alerts both agents when they edit the same file within 30 seconds. Single-operator focus, but the collision detection is a cheap, high-value steal for SAW's collaborative-code-access roadmap. https://github.com/aannoo/hcom
- agentscope-ai/AgentTeams (5.5k stars, Apache-2.0, v1.2.2 Aug 2026) uses Matrix rooms as its entire collaboration substrate: humans, a Manager agent, and Worker agents all live in visible Matrix rooms (bundling Tuwunel server + Element Web client), with a credential gateway so workers never see real secrets. It is manager/worker orchestration rather than peer developers with personal agents, but Matrix-as-transport directly answers SAW's 'invite by email, no Tailscale, self-hostable' relay requirement off the shelf, including access levels via rooms and power levels. https://github.com/agentscope-ai/AgentTeams
- claude-git-sessions (ingram-technologies) shares Claude Code sessions across a team through an orphan git branch — no server, no extra infrastructure, transcripts ride with the repo. The mechanism (a dedicated refs namespace synced through the existing git remote) is a local-first transport SAW could adopt for asynchronous thread sync while keeping its no-transcripts boundary, reserving the WebSocket relay for realtime only. https://github.com/ingram-technologies/claude-git-sessions
- Entire.io captures every Claude Code session as checkpoints on an entire/checkpoints/v1 git branch, indexed alongside commits, searchable, and resumable by a coworker 'exactly where you or a coworker left off' — the strongest execution of 'threads synced with the codebase,' but built on sharing full session data, the exact thing SAW's boundary forbids. https://github.com/entireio/cli
- Linear's agent platform makes third-party agents (Claude Code, Devin, Cursor, Copilot, Codex) first-class workspace teammates with profiles and activity pages; assigning an issue to an agent is a webhook trigger and agents don't consume billable seats. Atlassian is doing the same via Jira for Slack (thread → context-rich work item → assign to coding agent). Both validate SAW's thread↔epic/story connector plan and provide the integration pattern (issue-assignment webhooks). https://linear.app/agents and https://www.atlassian.com/blog/company-news/ai-sdlc
- Orchestration frameworks are not competitors: CrewAI (role-based crews), LangGraph (production graph orchestration), AutoGen (now in maintenance mode; Microsoft points new users to Microsoft Agent Framework) all coordinate agents inside one application for one operator — none model multiple humans each owning an agent. https://pickaxe.co/post/crewai-vs-langgraph-vs-autogen
- Google's A2A protocol passed 150 supporting organizations, is natively integrated in Azure AI Foundry, Amazon Bedrock AgentCore, and Google Cloud, and moved to the Agentic AI Foundation in Aug 2026 (JSON-RPC 2.0/SSE, Agent Cards for capability discovery). It targets enterprise service-to-service agent delegation with no notion of human-owned peer agents or team rooms — a future interop layer for SAW, not a competitor. https://opensource.googleblog.com/2026/04/a-year-of-open-collaboration-celebrating-the-anniversary-of-a2a.html
- MCP's 2026-07-28 spec (largest revision since launch) went stateless, added a formal extensions framework with reverse-DNS identifiers and independent versioning, moved Tasks (long-running agents) into an official AWS-contributed extension, and introduced MCP Apps (server-rendered interactive UI in the client). SAW's 5-tool MCP surface remains the right integration point; the extensions framework offers a path to standardize a 'team thread' extension, and MCP Apps could render SAW's room UI inside any MCP client. https://blog.modelcontextprotocol.io/posts/2026-07-28/
- The gap nobody fills: agent-mediated human-to-human communication where each developer keeps their own agent (in their own tool), threads are per work item and synced with the codebase, the teammate's agent reads the thread and surfaces answers inside that teammate's own conversation, and only distilled messages plus git refs ever cross — local-first, cross-vendor, privacy-bounded. Every existing player picks exactly one of: shared agent in a chat platform (Slack Code, Devin, Copilot), raw transcript sharing (Amp, Entire), single-operator orchestration (Claude agent teams, Copilot/Codex apps, hcom), or bare protocol (A2A, MCP).

## Recommendation
SAW v1 should not compete with Slack Code as chat; it should double down on the composite nobody else can credibly ship: each developer keeps their own agent, per-work-item threads synced to the repo, cross-vendor (Claude Code + Cursor + Codex), local-first, with the strict messages-and-git-refs boundary as the headline privacy feature. Concretely: replace Tailscale by syncing thread state through the existing git remote via a dedicated refs namespace (claude-git-sessions pattern) for async, with Matrix as the optional off-the-shelf realtime/invite layer (AgentTeams proves it works, and rooms/power-levels map to SAW's team/project/1:1/group access levels); adopt Claude Code's cross-session messaging safety semantics (accept/hold/refuse inbound controls, messages never approve permissions) for cross-member steering; and add hcom-style same-file collision detection as the first increment toward thread-tied workspaces. Structure threads now so each can later bind to a Linear/Jira issue via their agent-assignment webhook APIs — that connector pattern is already standardized and validates the thread↔work-item model.

# context-sharing

## Summary
I researched five mechanisms for sharing an agent's context with teammates, grounding transcript claims in 432 real Claude Code session files on this machine and in SAW's existing code. Raw transcript sharing is a dead end as the thing that crosses: formats are per-vendor, unstable, huge (median 186 KB / ~45-50K tokens, max 25 MB), and universally flagged as secret-laden — but the local transcript is the ideal *source* to distill from, and SAW's Stop hook already receives transcript_path and parses the JSONL. Agent-maintained journals (the proven Claude Code auto-memory pattern) plus MCP resources (natively supported by Claude Code via @-mentions, and cross-agent since Cursor/Codex speak MCP) together deliver the "ask about my teammate's work" experience with small, human-inspectable payloads. CRDTs (Yjs/Automerge 3.0/Loro) are the right infrastructure for the later live-edited thread UI, not for v1's append-mostly threads; RAG is unnecessary at v1 scale where loading the relevant journal directly beats maintaining an embedding index.

## Findings
- (a) Raw transcripts, measured locally: this machine has 432 Claude Code session JSONLs under ~/.claude/projects/<slugged-cwd>/<session-id>.jsonl — median 186 KB (~45-50K tokens), p90 ~600 KB, max 25 MB (~6M tokens). Entry types observed: user, assistant, attachment, queue-operation, last-prompt, ai-title, custom-title, mode; keys include message, toolUseResult, gitBranch, cwd, parentUuid, version. Anthropic's docs say the entry format is internal and changes between releases — parse-and-share pipelines break on any update (https://code.claude.com/docs/en/sessions, https://www.adityabawankule.io/blog/claude-code-session-jsonl-format).
- (a) Vendor equivalents are all different: Cursor stores chats in SQLite (state.vscdb under workspaceStorage/globalStorage, bubbleId:/composerData: keys, format changed between 2.x and 3.0+; export needs third-party tools like github.com/somogyijanos/cursor-chat-export); OpenAI Codex CLI writes rollout JSONLs to ~/.codex/sessions/ with a metadata header line plus event lines (https://github.com/openai/codex/discussions/3827). Three incompatible, unstable formats means SAW would need per-vendor adapters if raw transcripts ever crossed.
- (a) Privacy: transcripts contain full source code, tool outputs including .env contents and error logs, file paths, and half-thoughts; every source flags them unsafe to share. Existing sharing tools confirm the hazard: claude-code-templates session-sharing uploads unencrypted JSON to x0.at with only manual redaction guidance (https://docs.aitmpl.com/advanced/session-sharing); the 'Session Share' skill does redaction + relative-path rewriting client-side (https://mcpmarket.com/tools/skills/session-share-for-claude-code); Lore offers URL-based sharing with workspace visibility (https://lore.link/blog/best-ways-to-share-a-claude-code-session). Consent is effectively all-or-nothing — no human reviews a 186 KB JSONL line by line. Note SAW's stated invariant already says 'never agent transcripts'.
- (b) Agent-maintained journals: the pattern is proven off-the-shelf in single-user form — Claude Code auto memory (MEMORY.md, on by default since v2.1.59, first 200 lines/25KB auto-loaded) and per-subagent memory (v2.1.33, Feb 2026) (https://blog.memoryplugin.com/claude-code-memory/). No turnkey multi-user product exists, but SAW already has the hook point: packages/cli/src/hooks/stop.ts receives transcript_path on every run and packages/cli/src/hooks/summary.ts already parses the JSONL (currently tool-use counts + git refs only). A distillation step there — cheap-model summarization of the run into a per-work-item journal entry (did/decided/open-questions/refs) — costs one Haiku-class pass per run to produce and only 150-400 tokens per entry to consume; a 20-run work item is ~3-8K tokens versus ~47K for one raw median transcript. Entries are small, human-readable markdown: reviewable before they cross, satisfying 'humans must see what crosses'.
- (c) CRDTs: Yjs (~920K weekly downloads, largest ecosystem; y-websocket provider could ride SAW's existing WebSocket relay), Automerge 3.0 (May 2025, Rust core, ~10x memory reduction, built-in history), Loro 1.0+ (fastest benchmarks, smallest encodings, rich-text + movable trees) (https://www.pkgpulse.com/guides/yjs-vs-automerge-vs-loro-crdt-libraries-2026, https://velt.dev/blog/best-crdt-libraries-real-time-data-sync). They solve concurrent multi-writer editing — but SAW v1 threads are append-mostly (messages + journal entries), which the existing relay already orders. Privacy is the real objection: continuous live sync removes the deliberate 'share' moment, cutting against inspectability. Right tool for the v2 UI's live-edited thread docs (brainstorm threads), premature for v1.
- (d) MCP resources: Claude Code natively supports MCP resources via @-mentions (format @server:protocol://resource/path, listed in the @ autocomplete, fetched on demand) and MCP prompts as slash commands, with list_changed refresh (https://code.claude.com/docs/en/mcp). SAW already ships an MCP server with 5 registered tools (packages/cli/src/mcp/server.ts) — adding resources/list + resources/read exposing thread journals (e.g. @saw:thread://T065) is a small delta. This is the only mechanism of the five that is natively cross-agent today: Cursor and Codex are also MCP clients, so one SAW server serves all three. Pull-based means token cost tracks exactly what is requested, and what is requested is the already-human-visible journal. The 2026-07-28 MCP spec revision (stateless core, cacheable list results) points in a favorable direction (https://blog.modelcontextprotocol.io/posts/2026-07-28/).
- (e) RAG over thread history: local-first options are mature — sqlite-vec, LanceDB, Chroma all run embedded, and 2026 consensus is that vector-enabled general databases (sqlite-vec) cover everything below billion scale (https://suparbase.com/blog/vector-databases-ranked-2026, https://shaharia.com/blog/choosing-embeddable-vector-database-go-application/). But at v1 scale (2 members, journals of a few KB per work item) direct loading or grep beats an embedding index; embeddings add an index to maintain, an embedding-model dependency (API embedding of a teammate's content is itself a consent question), and opaque retrieval — you cannot preview what the teammate's agent will see. Defer until thread history outgrows direct loading; when needed, sqlite-vec inside the existing local daemon keeps it local-first.

## Recommendation
SAW v1 should compose (b) + (d): extend the existing Stop hook to distill each run's transcript into a per-work-item journal entry (what I did / decisions / open questions / git refs, ~150-400 tokens), stage it locally for the human to see (with a per-user auto-share toggle), sync accepted entries over the existing relay as ordinary messages, and expose each thread's journal through SAW's existing MCP server as a resource (@saw:thread://<id>) plus a get_peer_context tool. This delivers "ask your agent about my work" — the teammate's agent pulls the journal deliberately and visibly — while raw transcripts never leave the machine, preserving SAW's stated boundary. Defer CRDTs to the UI phase (Yjs over the existing WebSocket relay when live-edited thread docs arrive) and defer RAG until journals outgrow direct loading (then sqlite-vec in the local daemon).

# connectors

## Summary
All three candidate ticket systems now have official, vendor-hosted remote MCP servers, so SAW should not build any ticket connector itself: Atlassian's Rovo MCP server (GA Feb 2026, OAuth 2.1 or API tokens, Cloud-only), Linear's server at mcp.linear.app/mcp (OAuth 2.1 with dynamic client registration, read-only endpoint variant, expanded Feb 2026 to initiatives/milestones/project updates), and GitHub's github-mcp-server (32.5k stars, remote at api.githubcopilot.com/mcp, ~80 tools including issues by default and a Projects v2 toolset). The gap MCP servers do not close: they are agent-pull only — nothing syncs when no agent is running, and nothing creates threads from tickets — while inbound webhooks require a public HTTPS endpoint the Tailscale-only relay lacks, plus per-provider admin friction (Jira: OAuth/Connect app with a 5-webhook-per-app cap and 100 per instance; Linear: workspace admin or admin-scope OAuth app). What SAW must build is therefore thin: a provider-agnostic thread↔ticket metadata binding replicated over the relay, hook-driven agent-mediated sync using each member's own credentials, an idempotency marker convention for ticket comments, and small config glue that installs the MCP server for both members. GitHub Issues is the clear v1 choice because it is repo-scoped exactly like SAW's rooms, both members already have GitHub auth, and gh CLI is a zero-install fallback.

## Findings
- Jira (official): Atlassian's Rovo MCP server went GA in February 2026 — repo github.com/atlassian/atlassian-mcp-server, endpoint https://mcp.atlassian.com/v1/mcp/authv2 (OAuth 2.1) or /v1/mcp (API tokens, required for headless/service use). Covers Jira, Confluence, JSM, Bitbucket, Compass; Jira tools grouped into read/write/JQL-search (create/update issues, bulk-create). Cloud-only — no Data Center support; permissions mirror the signed-in user's Jira roles. Sources: https://github.com/atlassian/atlassian-mcp-server, https://www.atlassian.com/blog/announcements/remote-mcp-server
- Jira (community): sooperset/mcp-atlassian (github.com/sooperset/mcp-atlassian, since Dec 2024) is the fallback for Jira Server/Data Center — self-hosted Docker, auth via API token, Personal Access Token, or OAuth 2.0; adds ops the official server lacks (status transitions, worklogs, epic linking, boards/sprints). Community-maintained, so a support liability if SAW ever points enterprise users at it.
- Linear (official): vendor-hosted at https://mcp.linear.app/mcp (Streamable HTTP; SSE endpoint being retired). Auth is the cleanest of the three: OAuth 2.1 with dynamic client registration, or a Linear API key as bearer token; a /mcp/readonly endpoint and 'read' scope give enforced read-only access. Tools: find/create/update issues, projects, comments; Feb 5 2026 release added initiatives, initiative updates, project milestones, project updates, project labels. Sources: https://linear.app/docs/mcp, https://linear.app/changelog/2026-02-05-linear-mcp-for-product-management
- GitHub (official): github/github-mcp-server, 32.5k stars, remote hosted at https://api.githubcopilot.com/mcp/ (OAuth or PAT) or local via Docker ghcr.io/github/github-mcp-server; already updated for the July 2026 stateless MCP spec. ~80 tools in 23 toolsets; the issues toolset (read/write issues, comments, labels, assignment, parent/sub-issues) is in the default toolset; the projects toolset (Projects v2: list/get projects, add/remove items, update fields e.g. To do → In progress, iterations, status updates) exists but is NOT enabled by default and must be opted into. Sources: https://github.com/github/github-mcp-server, https://github.blog/changelog/2025-10-14-github-mcp-server-now-supports-github-projects-and-more/, https://github.blog/changelog/2026-07-23-github-mcp-server-supports-the-next-mcp-specification/
- The structural gap MCP servers leave open: they are pull-based and only act while a member's agent is running. 'Stakeholder sees status without pinging you' and 'ticket-created-thread automation' need push — but inbound webhooks require a public HTTPS endpoint, which SAW's Tailscale-only relay does not have. Per-provider webhook friction confirms deferral: Jira Cloud webhooks can only be registered by Connect/OAuth 2.0 apps (5 webhooks per app per user per tenant, 100 active per instance since July 2024 — https://developer.atlassian.com/cloud/jira/platform/webhooks/); Linear webhooks require a workspace admin or an OAuth app with admin scope (https://linear.app/developers/webhooks); GitHub repo webhooks are the only trivial case (any repo admin, one REST call).
- What SAW must build beyond installing an MCP server (all thin, relay/CLI-side): (1) a provider-agnostic thread metadata field, e.g. ticket: {provider, repo|site|team, id, url}, set by a `saw thread link <url|#123>` command or saw_bind_ticket MCP tool and replicated like other thread metadata — this extends SAW's boundary from 'messages and git refs' to 'messages, git refs, and ticket refs'; (2) agent-mediated sync via SAW's existing hook architecture: when a run ends in a bound thread, the same agent upserts one status comment on the ticket through the member's own MCP connection — no SAW-held credentials, preserves local-first and per-user permissions; (3) an idempotency/attribution convention: wrap SAW-written ticket comments in a marker like <!-- saw:thread:<id>:<member> --> so two members' agents update one comment instead of spamming, and inbound sync can ignore SAW's own writes (loop prevention); (4) inbound pull-on-open: when a member opens a bound thread, a hook fetches ticket state and new comments via their auth and injects them through the existing unread-message mechanism; (5) config glue: `saw connect github` writes the MCP server entry (.mcp.json / claude mcp add) so both members get an identical connector; (6) a member↔provider identity mapping for attribution. True webhook-driven automation (ticket-created-thread, live status) waits until the relay has a public ingress — post-Tailscale.
- Why GitHub Issues wins for v1: SAW rooms are already scoped per git repo, so the binding collapses to just an issue number with the room's repo as default context — no new tenancy concept (Jira site or Linear workspace) enters the data model; both members of a shared repo necessarily have GitHub auth already, and gh CLI (present in every Claude Code environment) is a zero-config fallback when the MCP server is not installed; the official server is the most mature and battle-tested of the three; and when SAW later grows a public relay endpoint, GitHub webhooks are the only ones registrable without an app or admin ceremony. Linear is the strong second connector (best-designed official MCP, startup-audience fit); Jira last (Cloud-only official server, headless requires API tokens, DC needs the community server).

## Recommendation
Ship GitHub Issues as the one v1 connector: it is repo-scoped like SAW itself, requires zero new auth or tenancy concepts, and the official github-mcp-server (issues toolset on by default, gh CLI as fallback) is the most mature option. Build only the minimal binding: a ticket metadata field on threads ({provider:"github", repo, number, url}) set via `saw thread link`, hook-driven outbound sync where the member's own agent upserts a single marker-tagged status comment on the issue, and pull-on-open inbound sync through the existing unread-injection mechanism — no relay-held credentials, no webhooks, fully local-first. Design the metadata envelope provider-agnostically so Linear (second) and Jira (third) slot in without schema changes, and defer webhook-driven ticket-created-thread automation until the relay has a public ingress.

# surfaces

## Summary
Researched three UI-surface questions for SAW v1. (a) Embedding SAW's localhost room page in a VS Code webview is technically feasible on desktop (proven by extensions like vscode-live-frame that iframe localhost apps), but SAW's own server currently forbids it — server.ts sends X-Frame-Options: DENY / frame-ancestors 'none' — and webview portMapping cannot map ws:// URLs, so an embed needs a deliberate 'webview mode'; the stronger pattern (used by Graphite and GitLens) is to bundle the web UI into the webview and have the extension host, which can read .saw/daemon.json directly, talk to the daemon and postMessage state in. Publishing is low effort but must target BOTH the VS Code Marketplace (vsce, Azure/Entra publisher) and Open VSX (ovsx, Eclipse agreement) because Cursor and Windsurf install from Open VSX. (b) A single web app over multiple workspaces is the industry-validated shape — watchman (one per-user daemon, many watched roots), Docker Desktop (one backend, many contexts), Tailscale (one tailscaled + LocalAPI, thin CLI/web clients), and most directly Vibe Kanban (npx vibe-kanban: one local Rust+React server managing many repos and many coding agents) — and requires promoting SAW from per-repo daemon to a per-user daemon (or hub) with one origin, one token, and a per-repo daemon.json compatibility shim for hooks/MCP. (c) Prior art splits cleanly: per-process dashboards (ngrok localhost:4040) suit single-purpose tools, while every multi-project tool converged on single-daemon + thin surfaces.

## Findings
- VS Code webviews are extension-controlled iframes; an iframe-in-webview pointing at a localhost app works on desktop VS Code — jevakallio/vscode-live-frame (https://github.com/jevakallio/vscode-live-frame) does exactly this — but only if the app does not send frame-blocking headers. SAW's room page does: /Users/shreykatyal/Documents/shared-agent-workspace/packages/cli/src/web/server.ts sets 'X-Frame-Options: DENY' and 'frame-ancestors none' (deliberately, per T052/T057 token protection), so embedding requires adding a webview serving mode that allows a vscode-webview ancestor, or abandoning the embed approach.
- Webview 'portMapping' only maps http/https URLs, never websockets (microsoft/vscode issue #75854, https://github.com/microsoft/vscode/issues/75854). SAW's page depends on a /ws push channel with the token as a subprotocol. In a desktop embed the inner iframe's real origin is http://127.0.0.1:<port>, so SAW's isOwnOrigin check (packages/cli/src/daemon/local-auth.ts — accepts only http://localhost|127.0.0.1|::1 with exact port) would pass; but in remote contexts (SSH/WSL/Codespaces/vscode.dev) direct localhost iframes and ws break, so an embedded page only works reliably for local desktop sessions.
- Token handoff has a clean path that avoids embedding entirely: the extension host runs Node with workspace file access and can read .saw/daemon.json (mode 0600; holds port + per-run token; written by writeDaemonInfo in packages/cli/src/config.ts) exactly as hooks and MCP tools already do, then either inject the token into an embedded iframe URL or — the pattern Graphite and GitLens use — bundle the UI assets into the webview (localResourceRoots) and pass daemon state via webview.postMessage, with the extension host making the authenticated HTTP calls (no CORS, no origin checks, works in remote sessions). Graphite's extension explicitly 'builds directly off of the Graphite CLI' (https://graphite.com/docs/vs-code-extension).
- Marketplace effort is small but doubled: VS Code Marketplace needs an Azure DevOps publisher + vsce (note: global Azure PATs are retired Dec 1 2026; new publishing uses Entra ID auth — https://code.visualstudio.com/api/working-with-extensions/publishing-extension), and Cursor/Windsurf users install from Open VSX, which needs an Eclipse Foundation publisher agreement, GitHub-linked account, and the ovsx CLI (https://davidgomes.com/my-experience-with-publishing-an-extension-for-all-vs-code-ides/). One GitHub Actions workflow can publish to both; budget roughly a day for account setup plus annual token renewal. Since SAW's stated audience includes Cursor users, Open VSX is mandatory, and note Cursor proxies Open VSX behind its own malware scan (https://cursor.com/help/customization/extensions).
- Native affordances an extension adds beyond the webview — and the reason to build one at all for a coordination tool: StatusBarItem (persistent unread-count / paused-agent indicator with click-to-open), TreeView/WebviewView badges on the activity bar icon, window notifications with progress for incoming steering messages, registerUriHandler for vscode://saw.saw/... deep links (invite/join flows that open the editor pre-wired), file watchers on .saw/, and the ability to auto-spawn and supervise 'saw up' so users never run the daemon manually (https://code.visualstudio.com/api/references/vscode-api, https://code.visualstudio.com/api/ux-guidelines/overview).
- Multi-workspace single web app: the blocker today is one-daemon-per-repo with a per-run token injected into HTML served from that repo's own random port — N repos means N origins, N tokens, N websockets. Two viable shapes: (A) keep per-repo daemons and add a user-level registry (~/.saw/daemons.json) each daemon registers into, with a hub page aggregating via proxy; (B) promote to one per-user daemon serving many workspace roots from a single origin. Watchman is the canonical precedent for (B): one per-user daemon, many watched project roots, per-root config read from each root (https://facebook.github.io/watchman/docs/cmd/watch-project). (B) is strictly simpler for a dashboard (one origin, one token, one ws) and per-repo .saw/daemon.json can remain as a compatibility shim the hub writes so existing hooks/MCP callers keep working.
- Direct prior art for SAW's exact problem — a single local web app orchestrating multiple coding agents across multiple repos — is Vibe Kanban by Bloop AI (npx vibe-kanban; Rust backend + React frontend; runs Claude Code, Cursor CLI, Copilot, Gemini in parallel; git worktree per task; multiple repos in one workspace) (https://vibe-kb.com/, https://starlog.is/articles/ai-dev-tools/bloopai-vibe-kanban/). It validates the single-per-user-server, browser-tab-as-primary-surface shape and its worktree-per-task model is also prior art for SAW's future 'workspace tied to a thread' concept.
- Local-daemon + dashboard prior art maps to three patterns: (1) per-process dashboard — ngrok serves an inspection UI and API on localhost:4040 per agent process (https://ngrok.com/use-cases/share-localhost), which is SAW's current model and fine only while there is one thing to look at; (2) single backend + thick client — Docker Desktop runs one per-user backend with an Electron UI, extension frontends talking to backend services over a socket-like API (https://sensepost.com/blog/2023/an-offensive-look-at-docker-desktop-extensions/); (3) single daemon + thin multi-surface clients — Tailscale's tailscaled exposes a LocalAPI on a unix socket (/var/run/tailscale/tailscaled.sock) and the CLI and 'tailscale web' UI are both thin clients of it (https://tailscale.com/kb/1282/docker). Pattern (3) is the best fit for SAW: CLI, web app, and VS Code extension all as clients of one local API. Graphite shows the complementary split: CLI as local engine, rich review surface in a (cloud) web app, VS Code extension as a thin CLI-backed companion (https://graphite.com/docs/vs-code-extension).

## Recommendation
For v1, ship two surfaces backed by one local API: keep the CLI as the engine, and promote the daemon to a single per-user SAW daemon (watchman/Tailscale pattern) serving one localhost web app that shows all workspaces and threads on one origin with one token and one WebSocket — this is the multi-workspace unlock, it is where the thread UI should live, and Vibe Kanban proves the shape works for multi-agent/multi-repo; keep writing per-repo .saw/daemon.json so existing hooks and MCP tools are untouched. Add the VS Code extension as a thin companion, not a second UI codebase: bundle the same web app assets into a webview, have the extension host read .saw/daemon.json and proxy daemon calls via postMessage (avoiding the frame-ancestors/ws embedding traps entirely and working in remote sessions), and spend its real budget on native affordances — status-bar unread/paused indicator, activity-bar badge, notifications for steering messages, a vscode:// URI handler for invites, and auto-starting 'saw up'. Publish to both the VS Code Marketplace and Open VSX from one CI workflow, since Cursor and Windsurf users can only install from Open VSX. Defer any standalone Electron app and any cloud-hosted dashboard past v1 — every comparable tool got traction with CLI + local web + editor extension first.

# workspaces

## Summary
Across the 2026 landscape, every successful thread/work-unit-to-code binding is metadata over plain git branches, never a new sync primitive: GitHub links many branches to an issue via a sidebar table, Linear derives a deterministic branch name per issue for its agent sessions, Claude Code cloud sessions bind one conversation to one pushed branch ("teleport" = check out the branch + load the thread), Conductor's model is one task = one agent = one worktree, and Graphite encodes inter-work-unit dependency as stacked branches. The vision's exact phrase — "both agents can edit, not necessarily in parallel" — has a proven pure-git precedent in mob.sh: a WIP branch per session with commit-push handoffs, which maps directly onto SAW's messages-plus-refs channel. The alternatives that would give simultaneous editing (VS Code Live Share, now in maintenance mode; shared cloud dev environments) all move live file access or execution across the member boundary, violating Principles II and VI and the local-first preference. SAW's constitution (v1.2.0, .specify/memory/constitution.md) permits many-to-many thread-to-branch binding today because a ref is already legal payload; only a literally-shared single branch that both agents push to would require amending the branch-per-agent clause of Principle VI — and even that scheme would leave git-only sync itself intact.

## Findings
- Git worktrees are the 2026 industry standard for binding an agent task to an isolated checkout: Cursor built its Parallel Agents feature on worktrees, Claude Code's creator recommended 3-5 parallel worktree sessions (Feb 2026), and JetBrains shipped first-class worktree support in 2026.1. Crucially, worktrees are a member-LOCAL concern (one .git, many checkouts) with zero protocol impact — SAW can automate worktree-per-thread on each member's machine without anything new crossing the wire. (https://developer.upsun.com/posts/ai/git-worktrees-for-parallel-ai-coding-agents, https://www.augmentcode.com/guides/git-worktrees-parallel-ai-agent-execution)
- Conductor (conductor.build) is the closest existing product to SAW's thread-to-code problem, and its binding model is exactly 'one task = one agent = one worktree = one branch = one PR path', created and torn down automatically. It is single-user, which is the gap SAW fills — but it validates worktree-per-work-unit as the local half of thread binding. (https://www.conductor.build/docs/guides/git-worktrees/run-claude-code-with-git-worktrees)
- GitHub branch-linked issues prove the many-to-many shape SAW's vision asks for is just a metadata table: an issue's Development sidebar can link MULTIPLE branches, a branch link is replaced by its PR when one opens, and merging the linked PR auto-closes the issue. The binding is rows of (issue, ref) — precisely the payload SAW's Principle II already allows. Linear does the same with a deterministic branchName field per issue (e.g. eng-4222-fix-login-bug) that its agent coding sessions and GitHub automation key off. (https://github.blog/changelog/2022-09-07-link-existing-branches-to-an-issue/, https://linear.app/docs/coding-sessions)
- Claude Code cloud sessions are the strongest architectural precedent for SAW threads: each session (a conversation, i.e. a thread) is bound to one branch pushed to the remote, and 'teleport' materializes the thread locally by checking out that branch in any clone of the same repo plus loading the conversation history. Requirements are exactly SAW-compatible: branch pushed to remote, same repo, nothing but git and the thread transcript cross. (https://code.claude.com/docs/en/claude-code-on-the-web)
- mob.sh (Fast git handover, mob.sh) delivers 'both people edit, not in parallel' using ONLY git: `mob start` checks out a per-session WIP branch, `mob next` commits whatever state exists and pushes (handoff), the next driver pulls and continues, `mob done` squashes the WIP commits onto the base branch and deletes the WIP branch. It supports multiple WIP branches per base. This is the exact semantics the founder describes, implementable over SAW's existing messages+refs channel: the handoff signal is a message, the code moves by push/pull. (https://mob.sh/)
- Graphite's stacked-diff model (branch per logical change, each branch based on the previous, tooling auto-rebases the stack) is metadata layered over plain git branches — relevant when one SAW thread decomposes into dependent sub-changes, and further evidence that no one in 2026 invents a new code-sync primitive to bind work units to code. GitHub itself shipped native stacked PRs in 2026. (https://graphite.com/guides/stacked-diffs, https://byteiota.com/github-stacked-prs-public-preview/)
- Cloud dev environments (Codespaces, Coder, DevPod, Ona/ex-Gitpod) became the default home for autonomous agents in 2026, but as a SHARED workspace between two SAW members they fail the constitution three ways: a shared environment moves file access and execution control across the member boundary (violates Principle II), enables live co-editing outside git (violates Principle VI), and is server-side against the founder's local-first preference. Codespaces are also single-account — even GitHub's answer to sharing one is Live Share inside it. Reject as the binding mechanism. (https://devopsboys.com/blog/coder-vs-gitpod-vs-devpod-cloud-dev-environments-review-2026)
- VS Code Live Share is in maintenance mode at Microsoft and shares live editor buffers, terminals, and debug sessions — the literal 'live file editing between agents' and 'execution control' that Principles II and VI prohibit, and its human-latency CRDT model has no agent story. It is the cautionary precedent, not a candidate. (https://www.gethopp.app/blog/ides-for-remote-pair-programming)
- Jujutsu (jj) is gaining real traction for multi-agent work (workspaces per agent, first-class conflict objects, operation log) while remaining fully git-compatible — jj writes real git commits to the same remotes. For SAW it is a member-local tooling choice to stay compatible with, not a dependency: the wire format stays git refs. Watch, don't adopt. (https://docs.jj-vcs.dev/latest/git-compatibility/, https://wavect.io/blog/git-worktrees-vs-jujutsu-ai-coding-agents/)
- Constitutional analysis (/Users/shreykatyal/Documents/shared-agent-workspace/.specify/memory/constitution.md, v1.2.0): Principle VI contains two separable MUSTs — 'code sync between members MUST use git' and 'each agent MUST work on its own branch'. A thread↔ref binding registry plus sequential handoff via per-member branches satisfies BOTH as written (a ref is legal Principle II payload; agent B continues from agent A's pushed tip on B's own branch). Only a single shared branch that both agents push to would require amending the branch-per-agent sentence — and under the constitution's own versioning rules, relaxing that MUST is a MAJOR (redefining a principle), so v1 should not need it.

## Recommendation
V1 should add a thread-to-ref binding registry — each thread carries a base ref plus a set of bound branches under a `saw/<thread>/<member>` namespace, stored as many-to-many (thread, ref) rows, which is pure Principle II payload and needs no constitutional change. 'Both agents can edit' becomes a message-mediated baton, mob.sh-style but branch-per-agent-preserving: the active agent pushes, posts the tip ref plus a handoff message to the thread, and the other agent continues by branching from that tip on its own namespaced branch, with `mob done`-style squash-to-base when the thread resolves; locally, SAW binds each thread to a git worktree per member (Conductor's one-task-one-worktree model) so multiple threads coexist without collisions. This delivers sequential shared editing entirely through git push/pull and existing SAW messages. Only if the founder later insists on one literal shared branch both agents push to does Principle VI's 'each agent MUST work on its own branch' sentence need amending (to 'own working copy, with pushes to a shared thread branch serialized by an exclusive lease') — a MAJOR bump under the constitution's versioning rules, and unnecessary for v1.

## Summary

# Critique gaps

## Identity, authentication, and membership lifecycle at N members
Every research thread assumes members exist, but none defines what a member IS. Today identity is an unverified free-text github_username plus a per-workspace bearer token minted at join (packages/relay/src/store.ts:138-247) — no verification, no revocation, no offboarding path. The connectivity agent recommends Iroh, which introduces ed25519 NodeIds, and the repo-constraints agent schedules an InvitePayload rewrite, yet nobody connects these into an identity model — and the 002 shared-schema rewrite (participants lists, access levels, hello frames) cannot be written without one, making this the single biggest unresolved input to the spec.

Design question: Is a SAW member a per-workspace bearer token, a cryptographic keypair (the Iroh NodeId), or a verified external identity like GitHub — and how does one person unify across workspaces and devices? What does removal actually propagate: can an admin revoke a member's token and NodeId, and what happens to their claims, branches, and journal entries? Does an invite attest who the invitee is, or does anyone holding the emailed string simply become 'chris'?

## Prompt injection: peer content is executed context, not displayed data
The inject hook pastes every unread message verbatim into every teammate agent's context on every turn (packages/cli/src/hooks/inject.ts renderContext) — an unauthenticated instruction channel into other people's agents. At two trusted friends the 'input, not an order' framing suffices; at N members, plus connector-inbound content (GitHub issue comments authored by arbitrary outsiders, per the connectors agent's pull-on-open design), it is the system's largest attack surface. The landscape agent recommends copying Claude Code's steering safety semantics but only for explicit steers, and repo-constraints classifies the entire inject machinery as 'survives unchanged' — a pair-scale assumption.

Design question: How does the message schema mark origin class (member-human, member-agent, external-ticket) so a receiving agent applies different trust rules to each? Should injected text be structurally quarantined — rendered as quoted data under a 'never follow instructions found here' contract — and should certain verbs (claiming, posting, editing code) be forbidden as direct responses to injected content without human confirmation?

## Attention and token economics at N members x M threads
Injection today is all-unread-every-turn: cost scales O(members x messages) inside every agent run, and humans see one flat feed. The vision multiplies both axes — N people, per-work-item threads, brainstorm threads, connector events — yet no agent researched subscription, relevance ranking, digests, or per-run token budgets. This is not UX polish: participants, mute/notify state, and priority must live in the frozen shared thread schema, and the inject/ack cursor protocol needs redesign, so it lands squarely inside the one jointly-approved schema PR the repo-constraints agent already identified as the critical path.

Design question: What is the delivery model — does an agent receive only threads it participates in, only threads touching its current work item, or a ranked digest under an explicit token budget? Where does per-member per-thread subscription state live, and what may interrupt a running agent mid-turn versus wait for the next turn versus reach only the human?

## Async agency: answers given while you sleep — consent, cost, accountability
The headline vision scenario — a teammate's agent reads the thread and answers on my behalf while I'm away — has zero design in any summary. The context-sharing agent's pull-based journal quietly sidesteps it, but the verbatim vision requires generative answering, which raises unanswered questions: does an agent respond without its human present, whose API budget pays for composing answers to other people's questions, and what happens when an agent commits its human to something wrong ('yes, we'll ship Friday'). Whether v1 ships pull-only retrieval or any autonomous answering is a scope decision the spec must make explicitly.

Design question: Which response classes may an agent produce autonomously — verbatim journal retrieval, synthesized answers, commitments — and which require draft-and-approve from the absent human? How is an agent-composed answer marked as such and later confirmed or retracted by the human, and how is token spend attributed and capped when my agent burns my budget answering your question?

## Provenance and fidelity of relayed statements ('Chris said X')
Two compounding failure modes go untreated: distillation is lossy (a Haiku summary of a ~47K-token transcript is a claim about what happened, not a record), and attribution is soft (the relay trusts a bearer token; messages carry no signature — grep confirms no signing outside invite HMAC — and the receiving agent paraphrases again before the second human hears it). 'Chris said to do X' can be two agent interpretations deep with no path back to what Chris actually typed. Since the journal pipeline is v1's core data flow, fidelity affordances belong in the v1 message/journal schema, not a later hardening pass.

Design question: Should every crossing item carry a provenance chain — author identity, authored-by-human vs generated-by-agent vs approved-by-human, and a pointer to the verbatim original so a recipient's agent can quote rather than paraphrase when stakes are high? Does the human-review step for journal entries become mandatory for anything that will be presented downstream as 'X said' or 'X decided'?

## Relay availability and hosting lifecycle
The connectivity agent solved reachability (Iroh) but not availability: the relay is SQLite on one member's laptop. Every async feature in the vision — a stakeholder checking status at midnight, an agent answering while its human sleeps, connector sync — requires an always-on party, and 'scale to a corporation' makes one engineer's MacBook the team's system of record with no backup, no replication, and no answer to 'the host left the company.' No agent treated host selection, host migration, or data ownership and portability of the workspace store.

Design question: Does v1 explicitly accept host-online-only semantics and design offline queues around them, or introduce an optional always-on node — the same relay binary on a $5 VPS, or replication across member machines? What is the host-handoff procedure: can the store be exported and rehosted with tokens rotated, and who is entitled to that data when the host departs?

## Data lifecycle on an append-only store: retention, redaction, secret spills
The relay store is append-only with no delete or redact operation (verified: nothing in packages/relay/src/store.ts), which was tolerable for coordination pings but journals will move real project knowledge — decisions, open questions, architecture rationale — onto the relay indefinitely, and humans will eventually paste a secret into a message. Boundary validation scrubs at ingest but there is no recovery path after a miss, no retention policy, no removal of a departed member's data, and no export. The security posture quietly shifts from 'carries little' to 'accumulates the team's distilled context forever,' which the research never re-examined.

Design question: What redaction primitive does the protocol need — a tombstone/supersede frame that propagates through relay storage, member-local caches, and future injections — and who may invoke it, the author or an admin? Do workspaces get retention policies, and does group-scoped content need E2E encryption so a relay host (or Iroh public relay) cannot read threads it is not a participant in?

## Roles, moderation, and dispute machinery beyond mutual trust
Every current mechanism assumes symmetric peer trust: steering is advisory, claims are first-wins, anyone posts anything, and repo-constraints found no roles/permissions machinery anywhere to build on. The research flags access levels as a schema change but leaves the authority model undesigned — who creates or archives threads, removes members, overrides a claim held by someone on vacation, or is allowed to steer whose agent — and this model gates the Principle III constitutional amendment that must be settled before the 002 spec is approved.

Design question: What is the minimal viable role model for v1 (owner/member may suffice) and exactly which verbs does it gate — invite minting, member removal, thread archival, claim override, redaction? Does steering acquire a permission dimension (thread participants only, or explicit grants), and how is a claim dispute resolved when the holder is unreachable?

## Non-developer participants: the stakeholder who has no agent and no clone
The vision's 'stakeholder gets status without pinging you' and Jira-epic connectors imply participants who are PMs or managers — people with no repo clone, no daemon, no git auth, and no coding agent. Every research thread assumes the opposite: rooms are repo-scoped, membership requires running `saw join` on a machine, the surfaces plan serves localhost to daemon-runners, and the connectivity pick (Iroh) is explicitly Node-only and unusable from a browser. A read-only browser participant breaks the membership model, the transport choice, and the identity story simultaneously, so even deferring it must be a deliberate spec decision.

Design question: Can a member be agent-less and clone-less — a browser-only identity with read (or comment-only) access to selected threads — and what do they connect to, given iroh cannot reach a browser and the relay lives on someone's laptop? Does thread status need a projection surface (a shareable rendered status view) distinct from full room membership?

## Mixed-version operation and live-data migration (partially treated)
Repo-constraints proposed adding a protocol version to the hello frame but stopped there. SAW is self-hosted and members upgrade independently, so the 002 schema rewrite guarantees a window where an old daemon speaks me/peer/any at a new relay or vice versa; and existing SQLite rows — messages with no thread_id, work_items keyed by free-text tag, in-flight claims — need a defined backfill or the first upgrade bricks the workspace for whichever member updates second. At N members a flag-day upgrade stops being coordinable at all.

Design question: Is the compatibility policy lockstep (relay rejects old protocol versions with an upgrade instruction — tolerable at 2 members, painful at N) or a one-version translation window at the relay boundary? What is the canonical backfill — does every historical work-item tag become a thread, how does claim state carry over, and does migration run automatically on first new-version connect or via an explicit operator command?
